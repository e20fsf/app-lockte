# คู่มือภาพรวมโครงการ LOCKTE (ระบบทดแทน Access 5 โปรแกรม)

สรุปตั้งแต่เริ่มโครงการ (4 ต.ค. 2569) ถึง UAT แก้ครั้งที่ 4 (11 พ.ย. 2569) สำหรับผู้รับช่วงงาน ผู้ดูแลระบบ และทีมพัฒนา
รายละเอียดเชิงลึกอยู่ในเอกสารที่อ้างถึงในแต่ละหัวข้อ (เอกสารนี้ไม่ซ้ำเนื้อหา) · ข้อมูลจริงของลูกค้าไม่อยู่ใน git

## 1. โครงการนี้คืออะไร

โรงงานผลิตชิ้นส่วนเบรกและคลัทช์ ใช้โปรแกรม MS Access 5 ตัว โครงการนี้ถอดสเปคของเดิม แล้วสร้างระบบเว็บตัวเดียวมาแทน

| โปรแกรมเดิม | module ใหม่ | schema |
|---|---|---|
| พนักงาน (บุคคลและค่าแรง) | `Lockte.Hr` + `Lockte.Org` (ฝ่าย/แผนก/กะ) | `hr`, `org` |
| ผลผลิตและORDER | `Lockte.Prod` + `Lockte.Sales` (ลูกค้า/ส่งของ) | `prod`, `sales` |
| วัตถุดิบ (จัดซื้อ) | `Lockte.Purch` | `purch` |
| สอบเทียบ | `Lockte.Calib` | `calib` |
| เงินสดย่อย | `Lockte.Cash` | `cash` |

คำศัพท์ธุรกิจทั้งหมดอยู่ที่ [CONTEXT.md](../CONTEXT.md) (ใช้คำไทยตามที่ผู้ใช้พูดจริง)

## 2. สถาปัตยกรรมและการตัดสินใจหลัก (ADR)

- [ADR 0001](adr/0001-stack-aspnet-blazor-sqlserver-iis.md) — ASP.NET Core 10 + Blazor Server + MudBlazor + EF Core + SQL Server บน IIS (Windows Server); PDF ทำจากหน้า Razor แปลงด้วย Playwright/Chromium
- [ADR 0002](adr/0002-modular-monolith-by-business-area.md) — แอปเดียว แบ่ง module ตามหมวดงาน ฐานข้อมูลเดียวแยก schema; module อื่นอ่านข้อมูลของ module เจ้าของได้อย่างเดียว
- [ADR 0003](adr/0003-audit-history-written-by-every-module.md) — ทุก module เขียนประวัติการแก้ไข (schema `audit`) admin เปิดดูได้
- [ADR 0004](adr/0004-pay-data-visibility-flag-per-user.md) — ข้อมูลค่าจ้างเห็นได้เฉพาะผู้ใช้ที่ admin ติ๊ก "ดูข้อมูลค่าจ้างได้" (admin เองไม่เห็น) คนอื่นเห็น `***` และพิมพ์รายงานที่มีค่าจ้างไม่ได้
- ผู้ใช้ราว 10 คน ใช้พร้อมกันราว 5 คน: ระบบจึงเรียบง่าย ไม่มีบทบาทซับซ้อน มีแค่ admin / ผู้ใช้ทั่วไป / ธงดูค่าจ้าง

โครงสร้างโค้ด: `src/Lockte.<Module>` ต่อ module, `Lockte.SharedKernel` (คอลัมน์ audit, rowversion, concurrency), `Lockte.Web` (host, login, เมนู, หน้าจอ, รายงาน), `Lockte.Migration` (เครื่องมือย้ายข้อมูลจาก Access), `tests/Lockte.Web.Tests`

## 4. วิธีทำงาน (workflow)

1. **ถอดสเปคก่อน** (legacy-first): เอกสารโปรแกรมเดิมครบก่อน คำถามเรื่องระบบใหม่เลื่อนไปทีหลัง (`specs/<โปรแกรม>/`, `specs/print-forms.md`)
2. **ตั๋ว → session ผู้พัฒนา → PR**: ทีละตั๋ว แต่ละตั๋วมี session ของตัวเอง (worktree แยก) เขียนโค้ด+เทสต์ เปิด PR เข้า `develop`
3. **ผู้ประสานงานตรวจ**: merge `develop` + PR ใน worktree ชั่วคราว รัน `dotnet test` ทั้งชุดกับ SQL เครื่อง dev (.55) แล้วรายงานผู้ใช้ **ผู้ใช้อนุญาตก่อนจึง merge** (`gh pr merge N --merge`)
4. **ข้อกำหนดบังคับ**: รายงานใหม่ต้องจัดประเภทใน `Reports/PayReportRoutes.cs` (ไม่งั้น `PayAccessTests` ล้ม); ข้อมูลที่เป็นชื่อ/เลขจริงห้ามเข้า git, issue หรือเทสต์
5. **ข้อมูลเดิมที่ผิด**: ออกแบบให้ถูก ไม่คงข้อบกพร่องของ Access ไว้ แล้วออกรายงาน DQ ให้ลูกค้าตัดสินใจ (ดู `docs/migration/`)
6. Branch: `main` (ปล่อยจริง) ← `develop` (รวมงาน, เป้าหมาย PR) ← `feature/*`, `fix/*`

## 6. การย้ายข้อมูลจาก Access

- เครื่องมือ `src/Lockte.Migration` (รันบน PC อ่านสำเนา `.accdb`): `--program all|employee|order|cash|purch-master|purch-history|calib`, ต้องใส่ `--confirm <ชื่อฐาน>`, ทำงานแบบลบแล้วโหลดใหม่ (ซ้ำได้ผลเท่าเดิม ~10 นาที), ตัวแปร `LOCKTE_MIGRATION_SQL`
- ไฟล์ `--map` (CSV `kind,legacy,code,name,prefix`) ใช้ใส่คำตัดสินจับคู่รหัสเก่า→ใหม่ เก็บนอก git (มีชื่อจริง)
- ผลรอบ 2 พ.ย.: ทุกตารางตรงกับต้นทาง (ต้นทาง = ไม่ย้าย + DQ + โหลด) รายการ DQ ที่ลูกค้าต้องตัดสินใจอยู่ที่ `source/work/real-run-1/DQ-ต้องให้ลูกค้าตัดสินใจ.md` (ลำดับแนะนำ: A2 สินค้าไม่อยู่ในทะเบียน → A1 ผลผลิต ธ.ค. 68 นับซ้ำ → A3 ลูกค้า ORDER ไม่ตรงทะเบียน → A7 พนักงานผลิต → C1/C2 สอบเทียบ → B1/B3 วัตถุดิบ)
- งวดค่าแรงที่ย้ายมาจากระบบเดิมเป็น "งวดที่ย้ายมา": พิมพ์ซ้ำได้ แก้/คำนวณใหม่ไม่ได้
- เอกสาร: `docs/migration/full-run.md` และไฟล์อื่นในโฟลเดอร์เดียวกัน

## 7. รายงาน PDF

- สร้างจากหน้า Razor แล้วพิมพ์ด้วย Playwright (Chromium) ฟอนต์ **Angsana New ทุกโปรแกรม** (ติดตั้งบนเซิร์ฟเวอร์ ไม่อยู่ใน repo เพราะลิขสิทธิ์; ถ้าไม่พบถอยกลับ TH Sarabun New และ log เตือน; ตรวจที่ `/health/reports`)
- ท้ายกระดาษกลางเป็นวันที่ไทย; ฟอร์มที่ต้องตรงของจริง (ใบลาออก สลิป ใบ OT ใบขออนุมัติสั่งซื้อ ฯลฯ) ปรับตามภาพที่ผู้ใช้ส่ง

## 8. การสร้างแพ็กเกจและติดตั้ง

รายละเอียดทั้งหมด: [deploy/README.md](../deploy/README.md)

**สร้างแพ็กเกจ (เครื่องนักพัฒนา; ใช้ .NET 10 SDK + Git + PowerShell ไม่ต้องมี Visual Studio)**
```powershell
git checkout develop; git pull origin develop
powershell -ExecutionPolicy Bypass -File .\deploy\Build-Package.ps1 -AppOnly   # อัปเดตเซิร์ฟเวอร์ที่ลงไว้แล้ว (~50 MB)
```
- ต้องรันจาก PowerShell (ไม่ใช่ Git Bash); ตัด `-AppOnly` เมื่อติดตั้งครั้งแรก (ใส่ Chromium ~170 MB); ใส่ `-HostingBundle <exe>` ถ้า server ไม่มีเน็ต
- ผลลัพธ์: `out\lockte-<วันที่>-<commit>[-app-only].zip` เป็นชุดสะสมเต็ม (ติดตั้งตัวล่าสุดตัวเดียวพอ)

**ติดตั้ง/อัปเดตบน server** (Administrator): แตก zip ด้วย `tar` ไปที่ path สั้น แล้วรัน `Install-Lockte.ps1`
- **อัปเดต: รันโดยไม่ใส่พารามิเตอร์** → คงค่า `C:\Lockte\config\appsettings.Production.json` และฐานข้อมูลเดิม (ถ้าใส่พารามิเตอร์ที่ไม่ตรงกับ config สคริปต์จะปฏิเสธ; `-ResetSettings` จะเขียนทับ config)
- แอปอ่านสำเนา config ที่ `C:\Lockte\app\appsettings.Production.json`; EF migration ทำงานอัตโนมัติตอนเริ่มแอป
- สคริปต์ช่วยบน server (นอก repo ที่ `C:\Temp\LOCKTE-App\server-setup\`): `Check-LockteServer.ps1` (ตรวจ), `Set-LockteSettings.ps1`, `Set-EmployerOffice.ps1`, `Set-PersonnelOfficer.ps1`, `Harden-LockteServer.ps1` (สำรองฐานข้อมูลรายคืน, ไฟร์วอลล์, HTTPS แบบ self-signed)
- ไฟล์ `.ps1` ที่มีภาษาไทยต้องบันทึกเป็น UTF-8 **มี BOM** (Windows PowerShell 5.1)

## 9. การตั้งค่าที่ผู้ดูแลต้องกรอก (ข้อมูล ไม่ใช่โค้ด)

- `Employer:Office`, `Employer:Workplace` (ที่อยู่ที่ใช้หัวสลิป/เอกสาร; ถนนของที่ตั้งโรงงานตั้งที่ `Employer:Workplace:Road`)
- `Employer:PersonnelOfficerName` (เจ้าหน้าที่บุคคลบนใบลาออก); ค่าตั้งต้นของบริษัท (ผู้จัดการ คร.2, เจ้าหน้าที่บุคคล, เบอร์สำนักงาน, ถนนโรงงาน) commit ไว้ใน `appsettings.json` — appsettings.Production.json และหน้า "ผู้ลงนามบนแบบฟอร์ม" ทับได้ (#462)
- ชื่อผู้ลงนามบนสลิป/ผู้จัดการแผนก (ตั้งในหน้าตั้งค่าของแอป), ชื่อผู้จัดการสำหรับ คร.2
- เลิกใช้แผนกที่ไม่ใช้แล้ว (เช่น "ตกแต่ง2") ที่หน้าแผนกในแอป: แผนกที่เลิกใช้จะไม่โผล่ใน dropdown
- เปลี่ยนรหัสผ่านบัญชี Administrator ของ Windows และ `sa` ที่ยังเปิดอยู่

## 11. ข้อควรระวังที่เจอมาแล้ว

- `gh pr merge` บางครั้งตอบ 504 แต่ merge สำเร็จ — ตรวจสถานะด้วย `gh pr view` เสมอ (ตั๋วอาจต้องปิดเอง)
- เทสต์ที่ใช้ฐานร่วมกันอาจล้มเป็นครั้งคราว (flaky) — รันซ้ำก่อนสรุป
- Mermaid ใน specs: ชื่อ subgraph/erDiagram ภาษาไทยต้องใส่เครื่องหมายคำพูด
- ห้ามพิมพ์รหัสผ่านใน script ที่จะ commit; script ตรวจ/สำรองที่มีรหัสผ่านอยู่นอก repo เท่านั้น
- ขั้นติดตั้งที่ล้มเพราะใส่พารามิเตอร์: รันใหม่แบบไม่ใส่พารามิเตอร์
