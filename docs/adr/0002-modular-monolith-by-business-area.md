# แอปเดียวแบ่ง module ตามหมวดงาน, database เดียวแยก schema ตาม module

ระบบใหม่จะเริ่มจากโปรแกรมพนักงาน และผลผลิตและORDER แล้วเพิ่ม วัตถุดิบ / สอบเทียบ / เงินสดย่อย ภายหลัง เราจึงทำเป็น **แอป ASP.NET Core ตัวเดียว (modular monolith)** ที่ใช้ database เดียว, login ชุดเดียว และ deploy บน IIS ที่เดียว ภายในแบ่ง module ตาม**หมวดงานใน `CONTEXT.md`** ไม่ใช่ตามโปรแกรม Access เดิม เหตุผลคือ ผู้ใช้ประมาณ 10 คน, ทีมเล็ก และ server เครื่องเดียว ทำให้การแยกเป็นหลายแอปหรือหลาย service ไม่คุ้ม ขณะที่การแบ่งตามหมวดงานทำให้โปรแกรมที่จะเพิ่มในอนาคตเข้ามาเป็น module ใหม่ทั้งก้อน โดยไม่ต้องผ่า module เดิม

## Modules และเจ้าของข้อมูลหลัก

เจ้าของคือ module เดียวที่สร้างและแก้ข้อมูลนั้น module อื่นอ้างถึงด้วยรหัส และอ่านได้อย่างเดียว

| Module | schema | เป็นเจ้าของ | ระยะ |
|---|---|---|---|
| องค์กร | `org` | ฝ่าย, แผนก, กะ, เครื่องจักร, การแต่งตั้งหัวหน้าแผนก (แผนก → พนักงาน) และหัวหน้ากะ (แผนก × กะ → พนักงาน) | แรก |
| พนักงานและค่าแรง | `hr` | พนักงาน, เวลาทำงาน, การลา, ใบเตือน, งวดค่าแรง | แรก |
| ขายและส่งของ | `sales` | ลูกค้า, เขตการขาย, พนักงานขาย (บทบาทของพนักงาน), ORDER, การส่งของ | แรก |
| ผลิต | `prod` | สินค้า, กลุ่มสินค้า, ประเภทสินค้า, Lot ผลิต, ใบรายงานผลผลิต, สต็อกสินค้า | แรก |
| จัดซื้อและวัตถุดิบ | `purch` | ผู้ขาย, วัตถุดิบ, Lot วัตถุดิบ, สต็อกวัตถุดิบ | ถัดไป |
| สอบเทียบ | `calib` | เครื่องมือวัด, การสอบเทียบ | ถัดไป |
| เงินสดย่อย | `cash` | เงินสดย่อย | ถัดไป |
| (host `Web`) | `auth` | ผู้ใช้ระบบ (บัญชี login ของ ASP.NET Core Identity) | แรก |
| (host `Web`) | `audit` | ประวัติการแก้ไข และการเข้าระบบ (ทุก module เพิ่มแถวได้ ตาม ADR 0003) | แรก |

`auth` เป็นของ host ไม่ใช่ module ธุรกิจ เพราะ login มีชุดเดียวทั้งแอป module อื่นไม่อ่านตารางนี้ ใช้ชื่อผู้ใช้ปัจจุบันผ่าน `ICurrentUser` ใน `SharedKernel`

หัวหน้าแผนกและหัวหน้ากะเป็นข้อมูลของโครงสร้างองค์กร (แก้จากหน้าจอแผนก SCR-05) จึงอยู่ที่ `org` ซึ่งเก็บเพียงรหัสพนักงานที่อ้างถึง ข้อมูลของพนักงานยังเป็นของ `hr` (ตัดสิน 2026-10-18, #44)

"ผลผลิตและORDER" ของระบบเดิมแยกเป็นสอง module คือ **ขายและส่งของ** และ **ผลิต** ส่วนเมนูบนหน้าจอยังจัดกลุ่มให้คล้ายโปรแกรมเดิมได้

## กติกาการคุยกันระหว่าง module

- แต่ละ module เขียนข้อมูลได้เฉพาะตารางใน schema ของตัวเอง
- ถ้าต้องอ่านข้อมูลของ module อื่น ให้เรียกผ่าน public service ของ module นั้นแบบในโปรเซส (in-process) ห้ามใช้ DbContext หรือ entity ของ module อื่น
- อ้างข้อมูลหลักด้วย foreign key ข้าม schema ได้
- ไม่ใช้ message bus เรื่องที่เกิดต่อเนื่องข้าม module (เช่น การส่งของแล้วตัดสต็อกสินค้า) ใช้ event ภายในโปรเซสได้เมื่อจำเป็น

## โครง solution

- `Web`: host Blazor Server (และ Minimal API ในอนาคต ตาม ADR 0001)
- หนึ่งโปรเจกต์ต่อ module: แยกส่วน public service (สัญญาที่ module อื่นเรียกใช้), domain/logic และ data (DbContext ของ module)
- `SharedKernel`: เฉพาะสิ่งที่ไม่ใช่ข้อมูลธุรกิจ เช่น วันที่แบบ พ.ศ. และการปัดเศษเงิน
- เครื่องมือย้ายข้อมูลจาก Access เป็นโปรเจกต์ console แยกต่างหาก รันบน PC

## Considered Options

- **หลายแอปใช้ database ร่วมกัน (แยกตามโปรแกรมเดิม)**: ต้องมี login หลายชุด, deploy หลายที่ และแต่ละแอปแก้ตารางเดียวกันได้โดยไม่มีเจ้าของ
- **Microservices**: เพิ่มงานด้านโครงสร้าง (network, การ deploy, ความสอดคล้องของข้อมูล) โดยไม่มีประโยชน์ที่ขนาดนี้
- **DbContext ตัวเดียวทั้งระบบ**: ทำงานแรกได้เร็วกว่า แต่เมื่อเพิ่มโปรแกรมใหม่ จะเริ่มมีโค้ดที่แก้ข้อมูลของ module อื่นโดยตรงจนแยกกันไม่ออก
