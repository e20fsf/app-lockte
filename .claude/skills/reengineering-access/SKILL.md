# ถอดสเปคจาก MS Access

เป้าหมาย: ผลิตสเปคที่ **AI ตัวอื่นอ่านแล้วสร้างระบบใหม่ได้ถูกต้องโดยไม่ต้องถามกลับ** — AI ปลายทางจะไม่ถาม แต่จะเดาเติมช่องที่ขาดแบบ "ทั่วไป" ซึ่งไม่ตรงกับธุรกิจจริง งานของเราคือปิดช่องให้เดาน้อยที่สุด และทำให้ส่วนที่ยังต้องเดามองเห็นได้ชัด

skill นี้คือ **วิธีทำงาน** ที่ใช้ซ้ำได้กับทุกโปรแกรม Access — ไม่ใช่แม่แบบให้ทุกโปรแกรมต้องหน้าตาเหมือนกัน ความละเอียดของสเปคให้ได้สัดส่วนกับโปรแกรม (ดู "ความละเอียดที่พอดี")

## ไฟล์ใน skill นี้ (หนึ่งเรื่องต่อหนึ่งไฟล์)

| ไฟล์ | เรื่อง | อ่านเมื่อ |
|---|---|---|
| `references/principles.md` | หลักการเขียนสเปค | **ทุกครั้ง** ก่อนเริ่มเขียน |
| `references/workflow-access.md` | ขั้นตอนถอด + วิธีใช้สคริปต์ + รูปแบบที่พบบ่อยใน Access | ทุกครั้งที่ถอดโปรแกรม |
| `references/review-checklist.md` | checklist ตรวจคุณภาพ | ตรวจสเปคที่มีอยู่ และก่อนบอกว่าเสร็จ |
| `templates/*.md` | แม่แบบของสเปคแต่ละส่วน (1 ไฟล์ = 1 ส่วน) | ตอนสร้างไฟล์สเปค |
| `scripts/extract_access.py` | ดึงโครงสร้าง/SQL/macro/ตัวอย่างข้อมูลจาก .accdb | ขั้นแรกของทุกโปรแกรม |

## งานที่รับ

- **ถอดโปรแกรมใหม่** → `references/workflow-access.md` ตั้งแต่ขั้นที่ 1
- **ทำต่อจากที่ค้างไว้** → อ่าน `specs/<program>/README.md` (ตารางสถานะ) และ `open-questions.md` ก่อน แล้วทำไฟล์ถัดไปที่ยังไม่เสร็จ — อย่าเริ่ม extract ใหม่ถ้ามีผลใน `source/_extract/` อยู่แล้ว
- **ตรวจทานสเปคที่มีอยู่** → ไล่ `references/review-checklist.md` แล้วรายงานช่องโหว่พร้อมข้อเสนอแก้ เรียงตามผลกระทบ

## โครงสร้างผลลัพธ์

คัดลอกไฟล์จาก `templates/` ไปที่ `specs/<ชื่อโปรแกรม>/` — **หนึ่งไฟล์ต่อหนึ่งเรื่อง ห้ามปนกัน**:

```
specs/<program>/
├── README.md            ภาพรวม ขอบเขต + สารบัญและสถานะของทุกไฟล์
├── glossary.md          คำศัพท์
├── data-model.md        ตาราง (จัดกลุ่มตามการใช้งาน) ฟิลด์ ความสัมพันธ์ lookup คุณภาพข้อมูล
├── business-rules.md    กฎ BR-xxx + ตัวอย่าง + การปัดเศษ + state machine
├── screens.md           แผนผังเมนู + หน้าจอ SCR-xx
├── reports.md           รายงาน RPT-xx
├── integrations.md      import/export ระบบอื่น INT-xx
├── non-functional.md    สิทธิ์ ปริมาณ รูปแบบข้อมูล การย้ายข้อมูล
├── acceptance.md        เกณฑ์ตรวจรับ AC-xx
└── open-questions.md    คำถามค้าง Q-xx + การตัดสินใจที่ทำแล้ว
```

### ข้อบังคับเรื่องรูปแบบ (ห้ามดัดแปลงเอง)

ผู้ใช้คาดหวังให้ทุกโปรแกรมมีโครงสร้างเหมือนกันทุกประการ เพื่อเทียบกันได้และให้ AI ปลายทางรู้ว่าจะหาอะไรที่ไหน — ความ "สะดวก" ในการตัด/รวม/เปลี่ยนรูปแบบทำลายสิ่งนี้

1. **สร้างครบทั้ง 10 ไฟล์ตั้งแต่เริ่ม** ไฟล์ที่ยังไม่ได้เขียน ให้มีแค่หัวเรื่องจาก template + บรรทัด `> สถานะ: ยังไม่เริ่ม` — ลบแถวตัวอย่างสมมุติของ template ออก (ตัวอย่างเช่น T-Orders, BR-004 ใน template เป็นแค่ตัวอย่าง ห้ามเหลือในสเปคจริง เพราะ AI ปลายทางจะคิดว่าเป็นข้อมูลจริง) ถ้าเรื่องนั้นไม่มีในระบบ (เช่น ไม่มี integration) ให้คงไฟล์ไว้และเขียนว่า "ไม่มี" พร้อมหลักฐาน
2. **ใช้หัวข้อและคอลัมน์ของ template ครบทุกคอลัมน์ ตามลำดับเดิม** — ถ้าไม่มีค่าให้เว้นว่าง ห้ามตัดคอลัมน์ ห้ามรวมคอลัมน์ (เช่น ห้ามรวม "ชนิด" กับ "ขนาด")
3. **หนึ่งหัวข้อต่อหนึ่งหน่วย** — data-model: 1 ตาราง = 1 หัวข้อ แม้ตารางจะมีโครงสร้างซ้ำกัน (ให้เขียนตารางแรกเต็ม แล้วตารางที่เหลือเขียนว่า "โครงสร้างเหมือน T-xxx ทุกฟิลด์" + ส่วนที่ต่าง) — ใช้กับตารางที่ย้ายไประบบใหม่ ตารางที่ไม่ย้ายอยู่ในหัวข้อ "ตารางที่ไม่ย้าย" ท้ายไฟล์
4. **หัวข้อเพิ่มเติมที่ template ไม่มี** ใส่ได้ แต่ต่อท้ายไฟล์ หลังหัวข้อของ template ทั้งหมด
5. **ไม่ใส่เรื่องของไฟล์อื่น** — data-model บอกว่าข้อมูล *คืออะไร* (ความหมาย, รูปแบบ, ค่าที่เป็นไปได้); *ระบบทำอะไรกับข้อมูล* (ขั้นตอน, การคำนวณ, การย้ายสถานะ) อยู่ใน business-rules แล้วอ้าง ID

เมื่อเรื่องหนึ่งต้องพูดถึงอีกเรื่อง ให้อ้าง ID แทนการเขียนซ้ำ (เช่น screens.md เขียนว่า "validate ตาม BR-002" ไม่ใช่คัดลอกกฎมา) — ข้อมูลอยู่ที่เดียว แก้ที่เดียว ไม่ขัดกันเอง

ข้อมูลที่หลายโปรแกรมใช้ร่วมกัน (เช่น ตารางพนักงาน) ให้อยู่ใน `specs/_shared/` แล้วอ้างอิงจากแต่ละโปรแกรม

## ความละเอียดที่พอดี

ต้นทุนของสเปคคือเวลาของผู้ใช้ที่ต้องอ่านและตอบคำถาม จึงลงรายละเอียดตามความเสี่ยง ไม่ใช่ตามจำนวนวัตถุใน Access:

- **ละเอียดเต็มที่** — ทุกอย่างที่กระทบยอดเงิน/สต็อก/กฎหมาย, การคำนวณ, การเปลี่ยนสถานะ, การลบ/ย้ายข้อมูล — ต้องมีสูตร ตัวอย่าง และที่มา
- **สรุปเป็นตาราง** — หน้าจอกรอกข้อมูลธรรมดา (CRUD), รายงานที่เป็นแค่รายการข้อมูล, lookup — บรรทัดเดียวต่อชิ้นพอ
- **แค่ระบุว่ามีและไม่ใช้** — ตารางสำเนา/ทดลอง, ฟอร์มที่ไม่มีทางเข้าจากเมนู, ของที่ข้อมูลหยุดนานแล้ว — ใส่เป็นรายการพร้อมหลักฐาน แล้วถามผู้ใช้รวบเป็นคำถามเดียว

ห้ามคัดลอกผล extract ดิบ (รายการวัตถุทั้งหมด, SQL ทั้งไฟล์) เข้า `specs/` — มันอยู่ใน `source/_extract/` แล้ว และทำให้สเปคยาวจนหาสิ่งสำคัญไม่เจอ ถ้าต้องการตรวจความครอบคลุม ให้ใช้ INVENTORY.md ใน `source/_extract/` เป็น checklist

## กติกาการทำงาน

- **ยืนยันทีละไฟล์** — เขียนเสร็จแต่ละไฟล์ อัปเดตสถานะใน README แล้วสรุปสั้น ๆ ในแชทพร้อมรายการ `❓` ของไฟล์นั้น อย่ารอจนจบทั้งชุดแล้วค่อยถาม เพราะคำตอบเรื่อง data model มักเปลี่ยนการตีความ rule ที่ตามมา
- **ไม่ติดค้างเพราะรอคำตอบ** — ถ้าผู้ใช้ยังตอบไม่ได้ ให้ติดป้าย `❓` แล้วทำไฟล์ถัดไปต่อ สเปคที่มีป้ายครบยังใช้งานได้ ผู้ใช้ตอบทีหลังได้
- **ทีละโปรแกรม** — ห้ามข้ามไปโปรแกรมถัดไปจนกว่าผู้ใช้ยืนยันว่าโปรแกรมปัจจุบันเสร็จ
- **ไฟล์ต้นฉบับและผล extract อยู่ใน `source/`** (gitignore) — ใน `specs/` ใส่ได้เฉพาะตัวอย่างไม่กี่แถวที่จำเป็นต่อการอธิบาย
- **ไม่เปิดใช้ VBA/macro ของไฟล์เอง** — ถ้าต้องการโค้ดที่สคริปต์ดึงไม่ได้ ให้ผู้ใช้เป็นคนดึงจาก Access ของเขา (วิธีอยู่ใน workflow-access.md)
- **ก่อนบอกว่าเสร็จ** ไล่ `references/review-checklist.md` และถามตัวเองว่า *"ถ้านักพัฒนาที่ไม่เคยเห็นระบบเดิมเขียนโปรแกรมจากเอกสารนี้อย่างเดียว เขาต้องเดาตรงไหนบ้าง?"* — ทุกจุดที่ต้องเดา = เขียนเพิ่ม หรือติด `❓`
- skill นี้ทำสเปคเท่านั้น ไม่เขียนโค้ดโปรแกรมใหม่
