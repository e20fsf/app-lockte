# Quality Checklist

ไล่ทุกข้อก่อนบอกผู้ใช้ว่าสเปค "เสร็จ" — ถ้าข้อไหนไม่ผ่าน ให้แก้ หรือเพิ่มเป็น `❓` ใน open-questions.md

## ตรงตามรูปแบบ (ตรวจก่อนข้ออื่น)
- [ ] มีครบ 10 ไฟล์ตาม `templates/` — ไฟล์ที่ยังไม่เขียนมี `> สถานะ: ยังไม่เริ่ม`; เรื่องที่ไม่มีในระบบเขียนว่า "ไม่มี" พร้อมหลักฐาน
- [ ] ไม่มีแถวตัวอย่างสมมุติของ template หลงเหลือ (T-Orders, BR-004 ตัวอย่าง, Q-07 Flag2 ฯลฯ)
- [ ] ทุกตารางในไฟล์ใช้คอลัมน์ครบและเรียงตาม template
- [ ] data-model: ตารางที่ย้ายไประบบใหม่ 1 ตาราง = 1 หัวข้อ มี ID `T-xxx`; ตารางที่ไม่ย้าย (กลุ่ม D–F) อยู่ในหัวข้อ "ตารางที่ไม่ย้าย" พร้อมหลักฐาน
- [ ] ไม่มีผล extract ดิบ (รายการวัตถุทั้งหมด, SQL ทั้งไฟล์) ใน `specs/`
- [ ] หัวข้อนอก template อยู่ท้ายไฟล์

## ความครบถ้วน
- [ ] มีวัตถุประสงค์ ผู้ใช้ ขอบเขต และ Out of scope
- [ ] ทุกตารางในระบบเดิมอยู่ใน data-model: กลุ่ม A–C มีรายละเอียดฟิลด์ กลุ่ม D–F มีหลักฐานว่าทำไมไม่ย้าย
- [ ] ทุกรายการในเมนูหลัก (Switchboard) มี SCR/RPT/BR รองรับ
- [ ] วัตถุที่ extract ไม่ได้ (Extraction errors) ระบุใน README ว่าถอดจากอะไรแทน
- [ ] ทุกฟิลด์มี: ชนิด, ขนาด, null ได้ไหม, default, ความหมาย
- [ ] ทุก FK ระบุตารางปลายทาง และพฤติกรรมเมื่อลบ/แก้แถวแม่
- [ ] ทุก enum/สถานะระบุค่าที่เป็นไปได้ทั้งหมด + การเปลี่ยนสถานะที่อนุญาต
- [ ] ทุกหน้าจอระบุ: ใครใช้, ข้อมูลมาจากไหน, ช่องบังคับ, ปุ่ม/เหตุการณ์ทั้งหมด
- [ ] ทุกรายงานระบุ: พารามิเตอร์, เงื่อนไขกรองข้อมูล, การจัดกลุ่ม, ผลรวม, การเรียง
- [ ] ทุก query / form / report / module / macro ในระบบเดิมถูกอ้างถึงอย่างน้อยหนึ่งครั้ง หรือระบุว่าไม่ใช้แล้ว — ใช้ inventory จากสคริปต์ extract เป็นรายการตรวจ

## ความชัดเจน
- [ ] ไม่มีคำคลุมเครือที่ไม่มีนิยาม: "ประมาณ", "ตามความเหมาะสม", "ปกติ", "รวดเร็ว", "ฯลฯ", "เป็นต้น"
- [ ] ทุกการคำนวณมีสูตร, ลำดับขั้น, จำนวนทศนิยม, วิธีปัดเศษ, การจัดการค่าว่าง
- [ ] ทุก validation ระบุข้อความ error และสิ่งที่เกิดขึ้น (บันทึก/ไม่บันทึก)
- [ ] วันที่: ระบุว่าเก็บ/แสดง พ.ศ. หรือ ค.ศ., timezone, และ "วันนี้" อ้างเวลาเครื่องไหน
- [ ] ข้อความภาษาไทย: ระบุการเรียงลำดับ (collation) ถ้ามีการเรียงตามชื่อ
- [ ] คำศัพท์ใช้ตาม glossary คงที่ทั้งเอกสาร

## ตรวจสอบได้
- [ ] business rule สำคัญทุกข้อมีตัวอย่าง input → output ≥ 2 ชุด รวมกรณีขอบ
- [ ] มี acceptance criteria ที่วัดผลได้ (ไม่ใช่ "ระบบทำงานถูกต้อง")
- [ ] มีเกณฑ์เทียบผลกับระบบเดิมบนข้อมูลจริง

## ความซื่อตรงของข้อมูล
- [ ] ทุกข้อที่ไม่ได้ยืนยัน มีป้าย `🔍 อนุมาน` (พร้อมหลักฐาน) หรือ `❓ ต้องถาม`
- [ ] ทุก `❓` ปรากฏใน open-questions.md พร้อม "ผลกระทบถ้าเดาผิด"
- [ ] ทุก rule อ้างที่มา (ชื่อ form/query/module + ตำแหน่ง) เพื่อให้คนตรวจย้อนได้
- [ ] พฤติกรรมแปลก/บั๊กของระบบเดิมระบุว่าจะ "คงไว้" หรือ "แก้" — AI ปลายทางแยกไม่ออกว่าบั๊กไหนเป็นฟีเจอร์

## ความสอดคล้อง
- [ ] ID (BR/SCR/RPT/Q/AC) ไม่ซ้ำ และทุกการอ้างอิงชี้ไปยังสิ่งที่มีอยู่จริง
- [ ] ชื่อตาราง/ฟิลด์ในทุกไฟล์ตรงกับ data-model.md
- [ ] README สารบัญ/สถานะตรงกับเนื้อหาจริง
- [ ] แต่ละเรื่องอยู่ในไฟล์ของมันเท่านั้น ไม่มีกฎ/นิยามถูกคัดลอกซ้ำไว้หลายไฟล์ (ไฟล์อื่นอ้าง ID แทน)

## Smoke test สุดท้าย
อ่านสเปคโดยสมมติว่าเป็นนักพัฒนาที่ไม่เคยเห็นระบบเดิม แล้วจดทุกจุดที่ต้องเดา ถ้ารายการไม่ว่าง สเปคยังไม่เสร็จ
