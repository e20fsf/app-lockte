# หลักการเขียนสเปค

ใช้กับทุกโปรแกรม ทุกข้อมีเหตุผลกำกับ — เมื่อเจอกรณีที่หลักการไม่ครอบคลุม ให้ตัดสินจากเหตุผลนั้น

1. **ตรวจสอบได้ ไม่ใช่ฟังดูดี** — ทุกประโยคควรเขียน test ได้ "ตรวจสอบข้อมูลก่อนบันทึก" ใช้ไม่ได้ ต้องเป็น "`รหัสสินค้า` ห้ามว่าง ยาว ≤10 ตัว ห้ามซ้ำ ถ้าผิดแสดง 'รหัสสินค้าซ้ำ' และไม่บันทึก"

2. **ตัวเลขต้องมีวิธีปัดเศษและลำดับการคำนวณ** — ส่วนลดก่อนหรือหลัง VAT, ทศนิยมกี่ตำแหน่ง, ปัดแบบไหน, คำนวณต่อบรรทัดหรือต่อบิล ความต่างเล็ก ๆ ทำให้ยอดไม่ตรงระบบเดิม

3. **ทุก enum/สถานะต้องระบุค่าทั้งหมด** และการเปลี่ยนสถานะที่อนุญาต — ไม่งั้น AI จะประดิษฐ์สถานะเอง

4. **ใส่ตัวอย่างจริง** — rule สำคัญทุกข้อควรมี input → output ≥ 2 ชุด รวมกรณีขอบ (ค่าเท่าเกณฑ์พอดี, ค่าว่าง, ค่าติดลบ) ตัวอย่างไม่กี่ชุดมีค่ากว่าคำอธิบายหนึ่งหน้า และกลายเป็น test case ได้ทันที

5. **บอก "ทำไม"** — "ห้ามลบใบสั่งซื้อ ให้เปลี่ยนเป็น Void *เพราะ* บัญชีต้องตรวจย้อนหลัง" เมื่อ AI เข้าใจเหตุผล มันตัดสินใจกรณีที่สเปคไม่ครอบคลุมได้ถูกทาง

6. **บอกสิ่งที่ "ไม่ต้องทำ"** (Out of scope) — AI ชอบทำเกิน เช่น เพิ่ม login, API, ฟีเจอร์ที่ไม่ได้ขอ

7. **แยกข้อเท็จจริงกับการอนุมาน** — ติดป้ายทุกข้อที่ไม่ได้ยืนยัน:
   - `✅ ยืนยัน` — ผู้ใช้ยืนยัน หรือเห็นชัดในโค้ด/ข้อมูล (ระบุว่าแบบไหน — "โค้ดทำแบบนี้" ไม่ได้แปลว่า "ธุรกิจตั้งใจแบบนี้")
   - `🔍 อนุมาน` — สรุปจากหลักฐาน ยังไม่มีคนยืนยัน (ระบุหลักฐานด้วย)
   - `❓ ต้องถาม` — ไม่รู้ ต้องถามผู้ใช้ (ใส่ใน open-questions.md ด้วย)

   การเดาที่ไม่มีป้ายอันตรายที่สุด เพราะ AI ปลายทางจะถือเป็นความจริง

8. **ใช้ ID ทุกอย่าง** — `BR-012`, `SCR-03`, `RPT-05`, `INT-01`, `AC-02`, `Q-07`, `T-Orders` อ้างอิงข้ามไฟล์ได้ และติดตามได้ว่า rule ไหน implement/test แล้ว

9. **ใช้คำเดียวกันตลอด** — นิยามใน glossary แล้วใช้คำนั้นคำเดียว อย่าสลับ "ลูกค้า/ผู้ซื้อ/คู่ค้า" ถ้าหมายถึงสิ่งเดียวกัน

10. **เขียนพฤติกรรม ไม่ใช่การ implement** — บอกว่าระบบต้องทำอะไร ไม่ต้องบอกวิธีเขียนโค้ด ยกเว้น tech stack ที่ผู้ใช้กำหนด ให้ใส่ใน README หัวข้อ Constraints

11. **หนึ่งเรื่องต่อหนึ่งไฟล์** — ตาราง, กฎ, หน้าจอ, รายงาน, คำถามค้าง แยกไฟล์ตาม `templates/` ห้ามปนกัน (เช่น ห้ามเขียน business rule ลงใน screens.md — ให้อ้าง ID แทน) เพื่อให้คนและ AI หาเจอว่าเรื่องไหนอยู่ที่ไหน และแก้ที่เดียวไม่ขัดกันเอง

12. **ภาษา** — เขียนสเปคเป็นภาษาไทย ชื่อตาราง/ฟิลด์ใช้ตามต้นฉบับ (ไม่แปล เพราะต้อง map กับข้อมูลจริง) ถ้าชื่อเดิมไม่สื่อ ให้อธิบายข้าง ๆ
